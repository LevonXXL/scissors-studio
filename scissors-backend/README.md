# Scissors Studio — backend (Django + DRF)

Бэкенд для сайта/приложения Scissors Studio. Три приложения:

- **`pages`** — статические страницы деревом (MPTT): `Page` + `PagePicture`.
- **`salons`** — салоны (сейчас 2), с адресом и координатами для Яндекс.Карт.
- **`masters`** — мастера-партнёры, привязаны к салону.

## Установка

```bash
python3 -m venv venv
source venv/bin/activate  # Windows: venv\Scripts\activate
pip install -r requirements.txt

python manage.py migrate
python manage.py createsuperuser
python manage.py seed_demo_data   # необязательно: наполнит БД тестовыми данными
python manage.py runserver
```

Админка: http://localhost:8000/admin/
API: http://localhost:8000/api/v1/

## Модели

### `Page` (pages/models.py)

Дерево страниц через django-mptt. Поля:

- `title` — заголовок страницы (H1/контент).
- `meta_title` — заголовок для `<title>`, хлебных крошек и меню; если пусто — используется `title`. Доступ через `page.title_tag`.
- `meta_description` — тег `meta description`; также используется как краткое описание страницы в списках.
- `content` — тело страницы, CKEditor 5 (`django_ckeditor_5`).
- `url` — slug, генерируется автоматически из `title` через транслитерацию, если не заполнен вручную.
- `url_path` — полный путь от корня (`parent.url_path + '/' + url`), пересчитывается каскадно по всем потомкам при сохранении. **Важно:** глобально уникален, не только в рамках родителя — так же, как в референсном проекте chinese-russian.
- `parent` — родительская страница (`self`, MPTT).
- `position` — ручной порядок среди сиблингов.
- `is_published` — скрыть страницу, не удаляя.

`PagePicture` — обычный `ImageField` (без django-filer, для простой галереи из нескольких картинок на страницу он был бы избыточен). Поля: `image`, `alt`, `position`.

### `Salon` (salons/models.py)

- `name`, `address`, `phone`, `working_hours`.
- `latitude` / `longitude` — `DecimalField(max_digits=9, decimal_places=6)`. Хранятся отдельно от адреса специально: геокодировать адрес в координаты на лету на фронтенде — лишний внешний запрос и риск ошибки распознавания. Взять координаты просто: правый клик по нужной точке на yandex.ru/maps → «Что здесь».
- `coordinates` — свойство, отдаёт `[lat, lon]` для прямой передачи в виджет Яндекс.Карт.
- `is_active`, `position`.

**Яндекс.Карты на фронтенде:** нужен API-ключ (JavaScript API и HTTP Геокодер, https://developer.tech.yandex.ru/ — регистрация besplatного ключа с лимитом запросов). Координаты из `Salon.coordinates` передаются прямо в `ymaps.Map` без дополнительного геокодирования.

### `Master` (masters/models.py)

- `salons` — `ManyToManyField` на `Salon`: один мастер может работать в нескольких салонах (раньше был FK на один салон — исправлено, т.к. на практике мастер может работать и в Москве, и в Зеленограде). Цены за услугу у мастера при этом всё равно разные в разных салонах: `Service` уже привязан к конкретному салону через категорию, так что `ServiceStaffPrice(service, master)` однозначно определяет цену в конкретном салоне без доп. полей.
- `name`, `specialization`, `bio`, `photo`.
- `category` — Универсал/Модельер, Стилист/Топ-стилист, Арт-директор (соответствует уровням в текущем прайсе).
- `status` — Самозанятый / ИП, `inn` — опционально. Обязательно к показу на карточке мастера.
- `slug` — генерируется автоматически из имени через транслитерацию, с защитой от коллизий у тёзок (`anna-ivanova`, `anna-ivanova-2`, ...).
- `yclients_staff_id` — staff_id мастера в YCLIENTS, без него запись через API невозможна.
- `is_active`, `position`.

## API (DRF, `/api/v1/`)

- `GET /api/v1/pages/` — список опубликованных страниц (компактно, для меню/хлебных крошек).
- `GET /api/v1/pages/by-path/<url_path>/` — страница целиком по полному пути (например `by-path/o-nas/komanda/`) — так фронтенд резолвит произвольную вложенность разделов.
- `GET /api/v1/salons/` — список активных салонов (с логотипом и галереей фото).
- `GET /api/v1/masters/` — список активных мастеров; `?salon=<id>` — фильтр по салону (мастер, работающий в нескольких салонах, попадёт в выдачу по каждому из них).
- `GET /api/v1/service-categories/` — категории услуг с вложенными услугами и ценами (в т.ч. переопределениями по мастерам); `?salon=<id>` — фильтр по салону.

Пагинация — `PageNumberPagination`, 50 на страницу.

Схема API и интерактивная документация — `/api/schema/swagger-ui/` (Swagger UI) и `/api/schema/redoc/` (Redoc), через `drf-spectacular`.

## CORS

В `settings.py` разрешены `localhost:9000` и `localhost:9200` (дефолтные порты Quasar dev-server). Для продакшена сузить `CORS_ALLOWED_ORIGINS` до `https://scissors-studio.ru`.

## Медиатека (django-filer)

Логотип и фото салона (`Salon.logo`, `SalonPhoto`), фото мастера (`Master.photo`) и фото услуги (`Service.image`) — не обычные `ImageField`, а `FilerImageField` (связь с `filer.Image`). Причина: все эти фото приходят из одного источника (синхронизация с YCLIENTS, см. ниже) и нужна генерация превью «на лету» без ручного ресайза на каждой синхронизации — `django-filer` + `easy-thumbnails` дают это из коробки через свои шаблонные теги/API.

Это НЕ противоречит более раннему решению для `PagePicture` (там обычный `ImageField`) — там сценарий другой: несколько картинок вручную загружает контент-менеджер под одну CMS-страницу, без необходимости в общей медиатеке с дедупликацией.

**Важно для API-сериализаторов:** `FilerImageField` — это `ForeignKey`, а не `ImageField`. Обычный `ModelSerializer` отдал бы наружу ID связанной записи `filer.Image`, а не URL файла. Поэтому во всех сериализаторах, где есть такое поле, используется `core_utils/drf_fields.py::FilerImageUrlField` — отдаёт настоящий URL картинки.

## `sync` — синхронизация с YCLIENTS

YCLIENTS — источник правды по филиалам, мастерам-партнёрам, категориям услуг
и ценам. Раз в какое-то время (вручную командой или по расписанию через
Celery Beat — обвязка для этого уже есть в проекте, см. `booking`) данные
подтягиваются в наш Django и используются в админке/на сайте.

```bash
python manage.py sync_yclients                 # все салоны с заполненным yclients_company_id
python manage.py sync_yclients --salon-id 1     # один конкретный салон (наш id, не yclients_company_id)
```

Нужны переменные окружения `YCLIENTS_PARTNER_TOKEN` и `YCLIENTS_USER_TOKEN` —
в отличие от анонимного Booking Widget API в `booking/services.py` (там
достаточно только partner-токена), эндпоинты синхронизации отдают полные
данные компании (включая скрытых/уволенных сотрудников, финансовые поля
и т.п.) и требуют полной авторизации.

### Что и как синхронизируется

- **`sync/client.py`** — `YClientsDataClient`, отдельный от `booking.services.YClientsClient`
  клиент (другие эндпоинты, другой уровень авторизации): `company/{id}`,
  `staff/{id}`, `service_categories/{id}`, `services/{id}`. Те же оговорки
  про документацию, что и в `booking/services.py` — пути эндпоинтов собраны
  по структуре присланных вами примеров ответов, а не выверены по живой
  документации (она закрыта от автоматического парсинга).
- **`sync/images.py`** — скачивание и дедупликация картинок (кэш по URL в
  модели `SyncedImage`, чтобы не тянуть по HTTP одни и те же файлы при
  каждом прогоне). Не падает, если сеть/картинка недоступны — просто
  пропускает и пишет предупреждение в лог (это специально протестировано,
  см. `sync/tests.py`).
- **`sync/sync_service.py`** — маппинг JSON → модели. Явно **не трогает**
  поля, которых в YCLIENTS просто нет: `Master.status` (самозанятый/ИП) и
  `Master.category` (Универсал/Стилист/Арт-директор) — это бизнес-
  классификация под аудит соответствия модели независимых партнёров,
  задаётся вручную в админке один раз при создании мастера и не
  перезаписывается синхронизацией впредь.

### Реальные баги, найденные на ваших примерах ответов (не выдуманные заранее)

Оба всплыли только при прогоне на присланных вами `salon-zelenograd.json` /
`services.json` — без реальных данных их было бы легко не заметить:

1. **`image_group` — не список, а словарь** (`{id, entity, images: {basic: {path, ...}}}`),
   хотя по названию поля логично было бы предположить список изображений.
2. **`price` в `services[].staff[]` — диапазон `{min, max}`, а не число**,
   даже когда `min == max`. Модель `ServiceStaffPrice` сразу сделана с
   `price_min`/`price_max`, а не одним полем `price`.

### Тесты

`sync/tests.py` гоняет полную синхронизацию на реальных примерах ответов
(`sync/fixtures/yclients_samples/` — те самые файлы, что вы прислали),
с замоканными HTTP-вызовами к самому YCLIENTS API, но **не замоканным**
скачиванием картинок — специально, чтобы проверить, что при недоступной
сети (как в CI/CD без доступа к assets.yclients.com) синхронизация не
падает, а корректно пропускает фото. Из-за реальных (безуспешных) сетевых
попыток прогон занимает ~70 секунд — это ожидаемо, не баг.

## `booking` — интеграция с YCLIENTS

Архитектурное решение: YCLIENTS остаётся системой записи, но используется
только как API — свой интерфейс и дизайн на всём пути клиента, редиректов
на yclients.com/виджет нет.

- **`booking/services.py`** — `YClientsClient`, тонкая обёртка над Booking API
  YCLIENTS (`get_services`, `get_staff`, `get_available_dates`,
  `get_available_times`, `create_booking`). Формат авторизации
  (`Authorization: Bearer <partner_token>, User <user_token>`) подтверждён
  по официальному описанию, но **точные пути и структуру ответов
  эндпоинтов нужно свериться с developers.yclients.com, когда появится
  реальный partner-токен** — документация рендерится через JS и закрыта
  от автоматического парсинга, пути в коде собраны по нескольким
  неофициальным враппербиблиотекам. Клиент уже защищается от двух известных
  по этим враппербиблиотекам форматов ответа (`data` то плоский список, то
  словарь с вложенным ключом) — но это не гарантия, что формат не другой.
- **`booking/models.py`** — `Booking`, локальная копия записи. Нужна не для
  красоты, а потому что напоминания за 24ч/1ч — это периодическая задача,
  которой нужно быстро находить «кому сейчас пора написать» по индексу в
  своей БД, а не дёргать YCLIENTS на каждый тик.
- **`booking/reminders.py`** — чистая логика выбора записей под напоминание,
  без Celery — тестируется обычным `manage.py test`.
- **`booking/tasks.py`** — тонкая Celery-задача поверх `reminders.py`,
  подключена в `CELERY_BEAT_SCHEDULE` (каждые 5 минут).
- **`booking/push.py`** — сейчас просто пишет в лог; реальная отправка через
  Firebase Cloud Messaging появится вместе с мобильным приложением
  (Capacitor + `@capacitor/push-notifications`), когда будет что сохранять
  как device token.

Что нужно от заказчика/YCLIENTS-аккаунта Scissors Studio, чтобы это
заработало по-настоящему:

1. Партнёрский доступ — регистрация в маркетплейсе интеграций YCLIENTS
   (developers.yclients.com), после чего выдаётся partner-токен.
2. `company_id` для каждого из двух салонов → в `Salon.yclients_company_id`.
3. `staff_id` каждого мастера в YCLIENTS → в `Master.yclients_staff_id`.
4. Желательно — подписка на вебхуки YCLIENTS об изменении/отмене записи,
   чтобы `Booking.status` не расходился с реальностью, если клиент
   отменит визит по телефону, а не через наше приложение.

### Celery / Redis

Для реальной отправки напоминаний нужен запущенный Redis:

```bash
docker run -p 6379:6379 redis
celery -A scissors_studio worker -l info
celery -A scissors_studio beat -l info
```

Без Redis сам Django (сайт, админка, API) работает нормально — Celery
нужен только для фоновых задач-напоминаний.

## Что дальше (не входит в этот проект)

- Реальная сверка эндпоинтов `YClientsClient` с актуальной документацией и живым partner-токеном (см. предупреждение выше).
- DRF-эндпоинты и Quasar-компоненты для самого флоу бронирования (выбор мастера → услуги → даты → времени → подтверждение) — модели и клиент к YCLIENTS готовы, view/serializer поверх них ещё нет.
- Кастомный rich-text-виджет CKEditor 5 настроен по минимуму (`toolbar`) — стоит донастроить под реальные нужды контент-менеджера.
- В `django-ckeditor-5` не подключена загрузка изображений через сам редактор (`CKEDITOR_5_FILE_STORAGE` и т.п.) — картинки к статьям сейчас загружаются через `PagePicture`, а не инлайн в тексте.
